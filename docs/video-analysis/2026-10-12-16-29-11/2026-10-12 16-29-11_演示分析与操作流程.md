## 一、演示定位：先展示效果，再讲操作

这段视频的预期顺序是：先让观众看到一次真实、安全的投递从职位采集走到 BOSS 会话中的发送结果，再解释它解决什么问题，最后讲安装和操作。此前建议的“开场先讲痛点、随后安装、结尾才展示结果”不符合你的意图，这里已调整。

开头建议直接使用演示中约 09:50—11:47 的功能段落：设置计划投递 `1`、最多分析 `10` 个职位，展示采集和分析、人工确认清单、执行投递、最终结果。正式发布版还需要补录 BOSS 正确会话中的消息画面；当前视频只看到后台处理完成，不能把这段剪成“已送达”的证明。展示效果后，再回到“这是如何配置和操作的”。

## 二、演示实际表达的产品价值

演示希望解决两个问题：

1. 求职时需要查看、筛选和处理大量职位，重复操作耗时；
2. 一份固定简历和固定问候语无法覆盖候选人的全部技能，需要根据岗位要求选择更相关的经历与表达。

更准确的一句话介绍可以改为：

> Job Search Assistant 在用户本机保存简历与求职资料，通过 Chrome 扩展采集 BOSS 职位，完成规则筛选和岗位分析；用户确认企业、岗位与问候语后，再由扩展执行受控投递。

不要用“自动刷简历”“全自动海投”描述产品。这既不准确，也会削弱产品的安全感。

### P1：影响理解和转化

1. **开场用词不准。** “面试时刷很多简历”容易让人误解角色；应说“求职时浏览、筛选和投递大量职位”。
2. **卖点过于抽象。** “10 个技能只能体现 2—3 个”“千人千面”缺少具体示例。建议用一个岗位要求与一段候选人经历做前后对比。
3. **安装步骤说得太快。** “下载压缩包—解压—打开扩展程序—开发者模式—加载已解压目录”没有逐步解释，零基础用户容易卡住。
4. **账号来源没有说清。** 视频先由管理员创建测试用户，但口述像是用户可以自己注册。应明确：首次创建管理员，后续普通账号由管理员创建。
5. **模型配置概念混用。** 画面选择兼容 OpenAI 的接口形式，但实际填写 DeepSeek 地址。应解释“服务商”“模型 ID”“Base URL”“API Key”分别是什么，或直接提供 DeepSeek 预设。
6. **等待过程没有处理。** 简历识别期间有较长停顿，观众会认为系统卡住。视频应剪掉等待，产品则应显示阶段、进度、耗时预期和失败重试。
7. **投递前安全门讲得不够。** 应明确说明系统只采集与分析，直到用户核对登录身份、企业、岗位、问候语并确认后才发送。
8. **界面版本不一致。** 视频中左下角先出现 Web `v0.4.17`，后面变成 `v0.4.18`。正式演示应固定同一个已发布版本。
9. **浏览器环境过于杂乱。** 标签页、书签栏、系统通知、辅助插件通知和桌面元素分散注意力。建议使用独立 Chrome Profile 和干净桌面。
10. **结尾缺少明确下一步。** 应提供下载位置、安装文档、数据隐私说明和“首次只试投 1 个岗位”的建议。

### P2：口述表达问题

- “然后呢”“对”“OK”高频重复，削弱专业感；
- 多次边操作边临时组织语言，句子没有先说目标再说动作；
- “插件、扩展、自动化投递工具”等称呼交替出现，建议统一为“Job Search Assistant Chrome 扩展”；
- 介绍功能时先讲操作，后讲为什么，观众不容易形成整体心智；
- “会自动投递”表述过强，应强调“确认清单后执行受控投递”。

## 四、建议的标准用户操作流程

### 阶段 0：准备

1. 准备 Chrome、一个已登录的 BOSS 求职者账号，以及可用的大模型 API Key。
2. 启动 Job Search Assistant 服务并打开后台。
3. 首次部署创建管理员；普通用户账号由管理员创建。
4. 确认后台使用 HTTPS；不要通过公共网络使用明文 HTTP 提交密码、简历或 API Key。

完成标准：后台可打开，用户能够登录，页面显示明确版本号。

### 阶段 1：安装并连接扩展

1. 从 GitHub Release 下载 `job-search-assistant-chrome-mv3.zip`。
2. 解压 ZIP，保留完整文件夹。
3. 打开 `chrome://extensions`，开启“开发者模式”。
4. 点击“加载已解压的扩展程序”，选择直接包含 `manifest.json` 的目录。
5. 登录 BOSS 并打开职位搜索页。
6. 在后台“安装向导”生成 6 位配对码。
7. 在 BOSS 页面右下角控制台输入配对码并连接。
8. 核对后台个人档案姓名与 BOSS 页面右上角账号一致。

完成标准：后台显示扩展已连接、版本满足要求、BOSS 登录检查通过、身份一致。

### 阶段 2：配置模型

1. 进入“模型配置”。
2. 选择服务商或兼容协议。
3. 填写模型名称、模型 ID、API Key 和 Base URL。
4. 保存后执行连通测试。
5. 将验证通过的模型设置为主模型；如有需要再设置兜底模型。

完成标准：模型测试成功。日志和页面均不得回显完整 API Key。

### 阶段 3：导入并核对个人资料

1. 进入“简历库”，选择 PDF、DOCX、TXT 或 Markdown 简历。
2. 选择用于结构化识别的模型，点击“AI 识别并预览”。
3. 等待系统提取个人档案、技能、经历、教育和项目。
4. 逐项核对 AI 结果；删除杜撰内容，修正姓名、年限、公司和技术栈。
5. 确认后写入个人档案和项目库。
6. 设置默认简历；如果需要发送简历图片，确认首页预览可见并设为默认图片。

完成标准：个人档案和项目库内容真实、属于当前登录用户，简历预览可正常显示。

### 阶段 4：配置问候语与匹配规则

1. 在个人档案中填写默认问候语，内容只引用真实经历。
2. 在“匹配规则”中添加学历、经验、地点、薪资等规则。
3. 明确每条规则动作：仅提醒、降低匹配、排除或阻止投递，不能只写关键词而不确认动作。
4. 用一个模拟职位测试规则结果。

完成标准：默认问候语不存在他人经历；硬性条件命中后的系统动作符合预期。

### 阶段 5：首次安全试投

1. 进入“自动投递”，保持计划投递数为 `1`，最多分析职位数为 `10`。
2. 填写关键词、城市、求职类型、薪资、经验、学历、行业和公司规模。
3. 点击“开始首次安全试投”。
4. 扩展采集职位，本地服务执行规则和模型分析；此阶段不应发送消息。
5. 查看候选清单，逐项核对企业、岗位、匹配结论、问候语和简历策略。
6. 取消不希望联系的企业。
7. 再次核对个人档案姓名与 BOSS 登录身份。
8. 点击“身份与内容正确，开始投递”。
9. 切回 BOSS 沟通页验证问候语是否出现在正确会话；如发送图片，确认图片与默认简历一致。

完成标准：只处理 1 个已确认岗位；后台成功记录与 BOSS 实际会话证据一致。

### 阶段 6：扩大数量与复盘

1. 首次试投验证无误后，再逐步增加计划投递数，不要直接大批量运行。
2. 查看职位快照、失败原因和沟通结果。
3. 将“未通过规则”“身份不一致”“送达证据不足”作为明确失败，而不是算作成功。
4. 根据真实反馈调整筛选和问候语；不要根据一次运行自动改写个人经历。

完成标准：每次投递都能追溯到职位、规则、确认人、问候语、简历和送达证据。
